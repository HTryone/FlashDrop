### 22:23 ｜ Bug A 初修：对方在线灯要点发送才亮 · `25177f7`
- **根因**：发送端原本只在「开始传输」才建控制 WS，接收端连上来发的 `ready` 类通知，那时压根还没人听，丢了。
- **初修思路**：`genRoom()` 就开一个「在场侦听 WS」，专门听 `peer-joined`，对方一加入就亮灯。
- 这一步我们以为解决了，其实埋了个坑（见 22:55 的补刀）。

### 22:39 ｜ Bug B：接收端卡在 99% · `3317695`
- **根因**：发送端发完数据立刻 `POST /close`，relay 收到马上 `controller.close()` 截断还在排队的尾帧——接收端就差最后一帧，永远到不了 100%。
- **用户一锤定音**："以接收端为准，接收端 100% 再关流，发送完成以接收端为准。" 我们采纳了这个判断。
- **修复（relay 零改动）**：最后一段不再主动关流，等接收端收齐、回 `recv-done` 之后才关流。
- **事后核对**：git 实锤，之前三轮改动都没碰过 HTTP 传输主链路——这不是我们新引入的，是 relay 与尾帧入队的时序竞态，只是被我们这次碰巧根治了。

### 22:55 ｜ Bug A 补刀：在场 WS 连错了房间 · `1372755`
- **我们发现 25177f7 白修了**：那次 presence WS 连的是「基础房间」，而接收端连的是「段房间」（`房间码-s0`）。relay 的 `peer-joined` 是按房间隔离转发的——两个房间不同，灯永远收不到通知，只能等点发送时 `this.ctrl` 连上段房间才亮。
- **补刀**：presence WS 改连段房间、与接收端同房间；`startSend` 起传输即关掉它，把段房间槽位让给真正的控制 WS。
- 到这里，Bug A 才算真正闭环：**生成房间 → 对方点连接 → 灯立即亮，不用等你点发送。**

### 当晚深夜 ｜ 端到端实测（仅 HTTP，三技能连用）
- 房间 `UTPZEC` / `JDSKSN`，100MB 真实文件，agent-browser 双会话真 Chrome + 真实 OPFS 落盘 + SHA 校验：
  - ① 亮灯：接收端连上、发送端**未点发送**即「已在线 ✓」✅
  - ② recv-done 关流不卡 99%：落盘 104857600 字节 = 100%，SHA-256 与源文件完全一致，relay 房间已回收 ✅
  - ③ Bug A 同 ① ✅
- **速度真相**：100MB 实测 36 秒、平均 2.8 MB/s，下行不慢于上行。我们确认了——这是 relay + 跨太平洋链路的网络天花板（晚上的中国 ↔ 美国白天的带宽竞争），不是代码逻辑的问题。背压机制确实存在、也确实生效，但那一轮它不是主角。

### 01:0x ｜ 文档模块「下一篇 / 目录」跳回第一篇的 bug · `src/views/ModuleView.vue`
- **你点出来的**：点"下一篇"回到第一篇、点目录第二篇又自己弹回第一篇。
- **根因**：`onScroll` 滚动监听把所有文档的标题压成一张扁平列表，取最后一个"还滚得到"的标题当当前位置；可页面一次只渲染当前文档，其它文档标题在 DOM 里压根不存在，`getElementById` 拿不到就永远落选。滚回顶部时位置停在初始值——第一篇的第一个标题，于是把当前文档 ID 强行改回第一篇。
- **怎么修的**：滚动监听只认**当前文档**的标题做高亮，绝不跨文档切换；并改用视口相对坐标（`getBoundingClientRect`）判断当前标题，不再用会跨文档失准的 `offsetTop`。`vue-tsc` + `vite build` 全绿。
- **状态**：代码已改好、**尚未提交**（连同工作区里你自己改动的 `data.ts` 一起留在本地——按规矩我不碰你的内容数据）。
